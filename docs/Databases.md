# Databases: SQLite, MySQL/MariaDB, PostgreSQL

Qivot generates SQL through a small dialect layer (`QiSqlStatement` and its subclasses).
Historically it was SQLite-only; it now also targets **MySQL/MariaDB** and **PostgreSQL**.

You don't do anything special in your models — connect with the right Qt SQL driver and Qivot
picks the matching SQL generator automatically:

```cpp
// SQLite (unchanged)
QSqlDatabase db = QSqlDatabase::addDatabase("QSQLITE");
db.setDatabaseName("app.db");

// MySQL / MariaDB
QSqlDatabase db = QSqlDatabase::addDatabase("QMYSQL");     // or "QMARIADB"
db.setHostName("127.0.0.1"); db.setDatabaseName("app");
db.setUserName("root"); db.setPassword("secret");

// PostgreSQL
QSqlDatabase db = QSqlDatabase::addDatabase("QPSQL");
db.setHostName("127.0.0.1"); db.setDatabaseName("app");
db.setUserName("postgres"); db.setPassword("secret");

db.open();
QiConnection connection;
connection.open(db);                 // Qivot selects SQLite / MySQL / Postgres SQL here
```

Everything else — models, queries, joins, relations, migrations — is identical across backends.

## How the dialect is chosen

`QiConnection::open()` reads `QSqlDatabase::driverName()` and calls
`QiSqlStatement::forDriver()`, which returns:

| Qt driver | Generator | Notes |
|-----------|-----------|-------|
| `QSQLITE` | `QiSqliteStatement` | the original; unchanged |
| `QMYSQL`, `QMARIADB` | `QiMysqlStatement` | InnoDB / utf8mb4, `AUTO_INCREMENT`, `ON DUPLICATE KEY UPDATE` |
| `QPSQL` | `QiPgStatement` | identity keys, `lastval()` id, `ON CONFLICT` |
| anything else | `QiSqliteStatement` | safe fallback |

Most of the SQL (SELECT, JOIN, GROUP BY, LIMIT/OFFSET, UPDATE, DELETE, ON CONFLICT upsert) is
portable and lives in the base class. Each dialect overrides only what differs: column types, the
primary-key auto-increment clause, table options, and how the new row id comes back.

## What differs per backend

| Concern | SQLite | MySQL / MariaDB | PostgreSQL |
|---------|--------|-----------------|------------|
| Auto-increment PK | `INTEGER PRIMARY KEY AUTOINCREMENT` | `INT AUTO_INCREMENT PRIMARY KEY` | `INTEGER … GENERATED BY DEFAULT AS IDENTITY` |
| Strings — plain text | `TEXT` | `TEXT` | `TEXT` |
| Strings — key / unique | `TEXT` | `VARCHAR(255)` | `TEXT` |
| float / double | `DOUBLE` | `FLOAT` / `DOUBLE` | `REAL` / `DOUBLE PRECISION` |
| date / time | `DATE` / `TIME` | `DATE` / `TIME` | `DATE` / `TIME` |
| JSON (`QJsonObject`/`QJsonArray`) | `TEXT` | `TEXT` | `TEXT` |
| Booleans | `BOOLEAN` | `TINYINT(1)` | `BOOLEAN` |
| Blobs | `BLOB` | `BLOB` | `BYTEA` |
| New-row id | `lastInsertId()` | `lastInsertId()` | `SELECT lastval()` after insert |
| Upsert | `ON CONFLICT DO UPDATE` | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT DO UPDATE` |

**MySQL strings are clause-aware:** a string that is a `PRIMARY KEY` or `UNIQUE` becomes a bounded
`VARCHAR(255)` (so it can be indexed); every other string is `TEXT`, so long values are never
truncated. (SQLite and Postgres use `TEXT` for both — no length limit there.)

## Current limitations

- **Full-text search (FTS) is SQLite-only.** SQLite uses FTS5 virtual tables + triggers, which have
  no portable equivalent. On MySQL/Postgres, `createFtsIndex` is a no-op with a warning. Native FTS
  (MySQL `FULLTEXT`, Postgres `tsvector`) is a possible future addition.
- **`REPLACE INTO`** is SQLite/MySQL only; prefer `upsert()` on Postgres.
- **JSON is stored as `TEXT`** (a serialized string) on every backend — Qivot serializes
  `QJsonObject`/`QJsonArray` to a string and never queries into it. Native `JSONB`/`JSON` columns
  were tried but reverted: Postgres won't implicitly cast a *bound text parameter* into `JSONB`,
  which breaks parameterized inserts. `TEXT` round-trips correctly and portably everywhere.

## Testing

**Unit tests** (`tests/unittests`) include `DialectTests`, which assert the exact SQL each backend
generates. They need **no database** and run everywhere:

```bash
cd tests/unittests && qmake && make && ./unittests
```

**Integration tests** against real MySQL/Postgres need running servers. A Docker setup is provided
(see [`tests/integration/README.md`](../tests/integration/README.md)), and **CI runs them on every
push** — the `db-integration` job boots MariaDB + PostgreSQL as service containers, installs the
distro Qt SQL driver plugins, and runs the round-trip with `QIVOT_REQUIRE_DB=1` so a missing driver
or failed connection fails the build rather than skipping.
